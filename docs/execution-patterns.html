Patterns 1, 2, 3, 10 and 20: who plans, who converts, who launches, what runs

Every pattern starts with the human planning in a Claude Code (or Pi) pane inside Herdr. Only the convert and launch steps differ. Yellow = you, blue = a slash command or just recipe. Source of truth for the skills is .shared-llm/public/layers/slash-commands/; this page is the map. Regenerate it by hand when a pattern changes.

0. Pattern 20 · Pattern 10 without the agent in the middle

Same plan, same workflow.yaml, same phases, same hiring through the UpAgent hub. The only difference: the HIL agent you are talking to is the one that runs the phases. There is no plan-implementer pane. It hires the coder, then the reviewer, then the checks, loops on findings up to the retry count, moves to the next phase, runs finalize. You watch it, steer it, and compact it when it gets full. It keeps the same run notes the Pattern 10 implementer already keeps, nothing new.

PLAN      you + Claude Code (or Pi) in a Herdr pane:  /cc-plan (Pi: /do-plan) -> plan.md approved

CONVERT   same pane:  /cc-convert-pattern-20 --plan plan.md   (Pi: /do-convert-pattern-20)
            -> grades phases, you approve the split -> workflow.yaml

LAUNCH    same pane:  /upagent-pattern-20 --plan plan.md --workflow workflow.yaml
            no --offering / --effort: the controller is the agent you already started

RUN       this pane, phase by phase, following each phase's workflow file
            ├── phase 1: hire coder -> hire reviewer(s) -> hire checks
            │            findings back to the coder, up to  retries:
            ├── phase 2 .. N: same
            └── finalize workflow(s) on the whole result
          you talk to it directly; you /compact it when it fills up
          done when the last finalize passes

Pattern 10, for comparison:

          you <-> HIL (relay) <-> plan-implementer -> UpAgent workers
Pattern 20:
          you <-> HIL (runs the phases itself) -> UpAgent workers

Pattern 2, corrected

Pattern 2 is not "small work". It handles medium to large plans when you actively manage the pane. Its weakness is that the workflow is spoken each time. Pattern 20 keeps Pattern 2's shape and gives it the workflow file. If it works, it replaces Pattern 2 for anything with phases.

Converters must run in either harness

Settled: every converter ships for both Claude Code and Pi from one shared layer. /cc-convert-pattern-10 and /do-convert-pattern-10, /cc-convert-pattern-20 and /do-convert-pattern-20. You never switch panes to convert.

1. Patterns 1, 2, 3 and 10, start to finish

All four start the same way: you open Claude Code (or Pi) and plan. Only the launch step differs. Every controller pane must live inside Herdr (HERDR_ENV=1), and you start that pane yourself; automation never creates it.

Pattern 1 · HIL relay + plan-implementer (README "Flow 1")

PLAN      you + Claude Code pane (anywhere, remote app is fine)
          /cc-plan  -> research, grill, 2 adversary rounds -> plan.md approved
          (Pi: /do-plan)

CONVERT   none. Pattern 1 takes plan.md as is. No route.yaml.

LAUNCH    you start Claude Code in a Herdr pane (can be the planning agent
          if it already runs in Herdr, or a fresh pane; only the plan path matters)
          /hil --plan plan.md --offering <implementer-id> --effort <e>
            └── HIL runs just upagent-implementer-start
                  └── opens ONE plan-implementer pane in the control tab
                      (model = the --offering you picked)

RUN       plan-implementer reads plan.md, slices it, hires UpAgent workers
            ├── coder / reviewer / specialist hires via the Recruiter
            ├── questions  -> HIL quotes them to you, you answer, HIL relays
            └── your messages -> HIL drops them in the implementer inbox
          ends with implementer-result.json (completed / failed / blocked)

Pattern 2 · HIL is the implementer (README "Flow 2"; medium to large work with an active human; archetype for Pattern 20)

PLAN      small issue:  you in a Herdr Claude Code pane
          /upagent-pipeline rpi <issue-path-or-url>
            research worker -> plan worker -> you approve -> implement
          ad hoc:  /upagent-run "<task>"   one worker, one result

CONVERT   none.

LAUNCH    none. The pane you are already in IS the controller.

RUN       this pane hires UpAgent workers itself, holds the human gate,
          keeps the run log, implements in an isolated worktree.
          No second controller pane. you compact it when it fills.
          Weakness: the workflow is spoken each time, never the same twice.

Pattern 3 · phase leaders (README "Flow 3", used least)

PLAN      you + Claude Code pane:  /cc-plan -> plan.md approved

CONVERT   same agent or any Claude Code pane:
          /cc-convert --herdr plan.md  (Pi: /do-convert --herdr)
            -> run dir with plan.md + route.yaml (llm_profiles, per-phase lead/accuracy)
            -> validated by the runnable gate before it counts as converted

LAUNCH    you in a shell (inside Herdr):
          just run-start <run-dir>
            └── opens the controller pane and types /tui-control

RUN       controller loops the phases
            └── one /phase-leader pane per phase
                  └── Recruiter -> stage workers, reviewers, advisor
          phase-result.json per phase, run-status.md for the run

Pattern 10 · Pattern 1 + a workflow per phase (limited by plan size, see section 0)

PLAN      you + Claude Code pane:  /cc-plan -> plan.md approved

CONVERT   you in a Pi pane (same worktree):
          /cc-convert-pattern-10 --plan plan.md  (Pi: /do-convert-pattern-10)
            -> grades each phase easy / medium / hard
            -> workflow.draft.yaml, then workflow.yaml after you approve the split


LAUNCH    you start Claude Code in a Herdr pane:
          /upagent-pattern-10 --plan plan.md --workflow workflow.yaml \
                              --offering <implementer-id> --effort <e>
            ├── reads plan + workflow.yaml + every named workflow file
            ├── settles the open run choices with you (retry bounds, runners)
            ├── writes one frozen packet  <plan-dir>/pattern-10/<run-id>/plan.md
            └── then behaves exactly like /hil:  just upagent-implementer-start
                  └── ONE plan-implementer pane (the --offering you picked)

RUN       plan-implementer, phase by phase, reads the assigned workflow file
            └── hires the stages in order: coder -> reviewer(s) -> checks
                loops back to the coder on findings, up to  retries:
            └── after the last phase: the finalize workflow(s) you named
          HIL relay and inbox exactly as Pattern 1

So, answering your questions directly. You plan with one Claude Code agent. Converting is a second slash command in the same pane, for Claude Code or Pi. Launching is always a fresh Herdr pane where you type the launch command (or just run-start for Pattern 3). The launch command opens the controller pane for you; you never open the implementer or phase leader yourself.

2. Workflow YAML

phase-high-Sol.yaml

workflow: phase-high-Sol
kind: phase
tier: high
retries: 5            # repair loops after the first attempt, then ask you

stages:
  - role: coder
    offering: pi-gpt-5-6-sol
    effort: high
  - role: reviewer
    offering: pi-gpt-5-6-sol
    effort: high
    adversarial: true
  - role: checks
    workflow: validation      # the assignment's validation workflow

pass: every reviewer and checks stage passes
      on the same candidate
controller_requirements: controller-requirements.md

A custom workflow with a second reviewer and an audit

workflow: phase-high-Luna-double   # not bundled; put it in your own pool
kind: phase
tier: high
retries: 5

stages:
  - role: coder
    offering: pi-gpt-5-6-luna
    effort: max
  - role: reviewer
    offering: pi-gpt-5-6-sol
    effort: high
    adversarial: true
  - role: reviewer            # just another item
    offering: claude-fable-5-1
    effort: low
    adversarial: true
  - role: checks
    workflow: validation
  - role: auditor             # optional
    offering: pi-gpt-6-astra
    effort: medium
    retries: 2                # own counter for audit findings

pass: every reviewer, checks and auditor
      stage passes on the same candidate
controller_requirements: controller-requirements.md
# finalize-adversarial-Sol.yaml   (also -Fable, -Astra; one file per model, no choose-from)
workflow: finalize-adversarial-Sol
stages:
  - { role: reviewer, offering: pi-gpt-5-6-sol, effort: high, adversarial: true, scope: combined candidate }
pass: reviewer passes

# workflow.yaml  (the assignment)
phases:
  phase-1: phase-low-Luna
  phase-2: phase-medium-Luna
  phase-3: phase-high-Luna-double
validation: validate-Composer
finalize: finalize-adversarial-Fable        # or a list of two; both must pass, in list order
controller: delegated-implementer

Retries: the stages run once, top to bottom. Any finding goes back to the same coder and every later stage reruns; that is one repair loop, and retries is how many are allowed after the first attempt. A stage with its own retries spends that counter instead for findings it raised. When a counter is spent the controller stops and asks you. This stays an agent-followed contract, not a mechanical gate; attempt counts are recorded in run status.
