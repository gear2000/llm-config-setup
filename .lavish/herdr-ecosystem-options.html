Architecture decision · local source review · 19 July 2026

Do not replace Herdr.
Complete the stack around it.

Herdr remains the plan-and-phase control plane. Firstmate contributes proven supervision and lifecycle patterns. no-mistakes can become the final delivery and CI gate once the candidate branch is ready and shared infrastructure is locked.

Recommended: evolve Herdr in layers No wholesale replacement Shared AWS needs one exclusive lane
Keep

Herdr

Owns checked plans, phase order, stage gates, routing, durable receipts, backtracking, human decisions, and terminal authority.

Borrow patterns

Firstmate

Its strongest value is operational safety: wake queues, locks and beacons, restart reconciliation, backend ownership, and fail-closed teardown.

Final candidate gate

no-mistakes

Starts at a candidate-ready checkpoint while Herdr pauses and yields branch custody. It rebases, reviews, tests, documents, lints, pushes, opens the PR, and watches CI.

The central finding

Herdr, supervision, and delivery are different layers

A replacement comparison is misleading until the work is split into control, execution, supervision, and delivery.

Firstmate

Enhancement source

Do not import the distro wholesale. Port the mechanisms that close known operational gaps.

  1. Explicit named-session lab and a default-session tripwire for destructive Herdr tests.
  2. Queue an actionable wake before advancing detector state.
  3. Session lock plus freshness beacon. Extra sessions become read-only rather than competing owners.
  4. Created-versus-adopted ownership records before any pane cleanup.
  5. Fail-closed teardown that preserves dirty or unlanded work.
  6. One structured current-state snapshot for humans and tools.
Why this matters: Firstmate records a real cleanup bug where a label heuristic adopted and killed the captain's live Herdr pane. Structural ownership fixed it.

no-mistakes

Complement

Replace the ad-hoc final review, push, PR, and CI tail. Never start it during an active phase.

  • Fixed pipeline: intent → rebase → review → test → document → lint → push → PR → CI.
  • Daemon, SQLite state, disposable worktrees, approval gates, crash recovery, and AXI control.
  • The branch must be fully committed and Herdr must explicitly release custody first.
Two caveats: direct pushes to origin bypass the local named remote; and this public kit still needs a demonstrably independent final-diff reviewer before any push.

Required topology

Merge every phase worktree into one candidate branch. At the candidate-ready checkpoint, pause Herdr edits and hand that branch to the gate. Write run-terminal.json only after the gate and exact-SHA shared integration check pass.

Recommended target

Herdr stays the spine

Firstmate patterns harden Herdr itself. no-mistakes attaches at a candidate-ready custody boundary near the end of the run.

│   ├── Stage 4  moved out of ordinary build phases

│
├── Build Phase B
│   └── same lean lifecycle
│
├── Integration Construction Phase  [OPTIONAL]
│   └── only when real cross-slice production code remains;
│       use the same lean lifecycle, not an extra audit stack
│
└── CANDIDATE READY  (Herdr is paused, not terminal)
    └── no-mistakes attempt N owns the branch
        ├── rebase → review → test → docs → lint → push / PR
        └── PR CI acquires the shared-environment lease
            ├── deploy exact candidate SHA
            ├── run global AWS / end-to-end acceptance

                ├── replay forward from earliest affected phase
                └── new candidate → no-mistakes attempt N+1
Boundary: worktrees build code. Deterministic controllers run known checks and cleanup. The candidate branch accumulates the plan. Only PR CI holding the central environment lease may deploy to shared AWS.
Phase design correction

Verification is a stage. Construction is a phase.

No: Stage 3 is not a second adversarial review. Stage 2 judges the implementation. Stage 3 proves a narrow technical boundary with evidence. It may run hermetic contract, component, or local acceptance tests, but it must not deploy or mutate shared infrastructure. If it discovers missing production work, it fails back to Stage 1.

Keep in Stage 3

Mechanical-first seam verification

The route declares focused contract, component, or hermetic checks. A deterministic controller runs them. No shared AWS mutation. A fresh verifier is hired only when output is ambiguous or a failure needs attribution; missing production work revisits Stage 1.

Optional phase

Integration construction

Only add this phase when real cross-slice production code remains. Because it writes code, it still gets one implementation worker and one independent audit. It reuses the same mechanical seam and finalization path; it does not add a second stack of reviewers.

Shared acceptance

Keep it at candidate level

Onboarding the one test user, deploying to the one AWS environment, and global end-to-end acceptance happen once the candidate branch is ready. They require a central lease and can send the plan back to a responsible phase.

Recommended rename: Stage 3 — local seam verification. Reserve “integration construction phase” for writing cross-slice code, and “shared acceptance gate” for the one serialized AWS test lane.
Time and assurance budget

Do not pay an LLM for deterministic stages

Your concern is valid. The current five-stage phase can hire five workers even when three of those jobs are mostly commands, merge bookkeeping, and cleanup. Adding a mandatory final integration-construction phase would make the problem worse. The target should reduce LLM seats, not only add guardrails.

HIGH adds Stage 0 alignment only when risk earns it.

The expensive final loop remains, but early failures are still localized by phase evidence. Small plans stay small; phases remain meaningful vertical slices rather than tiny file edits.

Why Stage 2 is not duplicated: it independently judges code. Stage 3 becomes executable seam evidence, not another general reviewer. An optional integration-construction phase gets one audit only because it writes new production code; if no integration code remains, that phase does not exist.

Checked against the actual quality gates: remove the duplicate generic lint pass

The current CI definitions already run language lint broadly (Ruff for Python, lint plus TypeScript checks for the frontend, and Go lint/test gates); several Python pipelines also run MyPy. The candidate-level no-mistakes pipeline separately owns test → document → lint/static analysis before push, then watches CI. I found no explicit AST job in the current CI definitions. AST-aware inspection is an instruction inside Herdr's adversarial evaluator—not a separate deterministic pipeline stage. 

Stage 1   focused tests needed while implementing
Stage 2   independent semantic/adversarial audit; AST-aware when useful
Stage 3   only declared seam/contract checks not already proven above
Stage 5   merge + cleanup; do not rerun generic lint when candidate gate follows
CANDIDATE no-mistakes runs configured tests + lint/static analysis once
REMOTE    CI reruns its authoritative lint/type/test jobs on the pushed SHA

Fallback: if a run does not use no-mistakes, Stage 5 must keep the repository's normal green-check command so lint is not dropped. Local-versus-remote repetition inside no-mistakes is intentional: local catches failures before push; CI proves the exact shared candidate.

Conversion contract

The plan converter should recommend whether an integration-construction phase exists

Agreed: leave the original planning workflow alone. It produces one coherent big plan. The conversion step analyzes that plan, breaks it into Herdr phases and stage routes, evaluates verticality and parallelism, and recommends whether residual integration construction needs its own phase. The executor must never invent that phase after work starts.

A shared AWS test user or environment does not by itself require an integration-construction phase. It requires a serialized candidate-level acceptance gate. The phase is required only when production code still has to be written across the slices.

Converter must provide

Recommendation: required or not required. Evidence: the exact residual wiring, shared contracts, dependencies, file/resource collisions, and why no existing phase can own it.

Conversion review

The converter may use a Planish-style static grill to show the phase tree and recommendation, but this review belongs to conversion. The human accepts, removes, or reshapes it. A missing note accepts the recommendation; uncertainty remains visible rather than silently guessed.

Checker enforces

The checked plan records an integration assessment. “Required” must name the phase and dependencies. “Not required” must state where every cross-slice contract is owned.

Verified current gap: today's meta-plan-convert asks only whether each generated phase merges at Stage 3, 4, or 5, then emits the same five stage routes. It does not assess verticality or residual integration construction. Centralize the new analysis there: outcomes, seams, shared contracts, parallel file/resource ownership, phase accuracy, mechanical versus LLM stages, and residual production wiring. Record the recommendation as an H3 integration assessment before Phase 0, and extend meta-plan-check / the schema so “required” names a phase while “not required” proves ownership. The upstream big-plan prompt does not need this decision logic.

Plan quality loop

Make independent adversarial plan review the default final step of cc/do-plan

The human-approved draft should become a candidate plan, not immediately the final file. By default, the planning command sends it through two independent challenge-and-revision rounds via the UpAgent Hub, then returns the changed plan to the human for final approval. This strengthens the plan before either direct implementation or Herdr decomposition.

Default protocol 
cc/do-plan "<topic>"
└── research + conditional design + human HTML grill
    └── human accepts candidate plan
        ├── ask: adversary model/profile? (recommend opposite family)
        └── --adversarial-iterations 2  [default]
            ├── round 1: fresh plan-adversary review order
            │   └── planner revises + records finding disposition
            ├── round 2: fresh full-plan review of revised artifact
            │   └── planner revises + records finding disposition
            └── regenerate annotated HTML with adversarial diff
                └── final human approval → immutable plan.md

The correct flag spelling is --adversarial-iterations. Accept 0 as an explicit opt-out; cap unattended rounds so a reviewer cannot create an endless planning loop.

Model independence
  • At candidate-plan finalization, show the planning model and ask which UpAgent review profile to use.
  • Recommend an independently configured model family, but do not hard-code a provider, model, or effort into the future planning workflow—the human chooses it for that run.
  • If the selected reviewer matches the planning model family, warn and ask for an explicit confirmation or a different profile.
  • A supplied --adversary-profile skips the question but must still resolve through the Hub roster.
Separate persona: add a plan-adversary agent. Do not reuse the current adversarial-evaluator unchanged—it audits finished code against a plan, whereas this role challenges feasibility, missing decisions, phase boundaries, testability, rollback, parallel safety, and acceptance criteria inside the plan itself.

Human authority and durable evidence

Each reviewer is read-only and writes a typed review result through the Hub. The planner owns revisions, but must disposition every finding as accepted, rejected-with-reason, or human-decision-required. Material product or architecture forks pause immediately for the human; they are never “resolved” by reviewer consensus. Preserve plan-candidate-vN.md, each review receipt, and a revision diff. Only the post-review human approval promotes the final plan.md.

Full-command behavior: cc/do-full inherits the same default of two adversarial rounds. It does not implement a second review loop; it calls cc/do-plan once, waits for final human approval, then follows --execute-direct or --execute-with-herdr. With neither flag, the final review asks which path to take or whether to stop. Execution flags preselect the path; they never bypass final human plan approval.
Internal Herdr roles

herdr-control owns the plan; herdr-phase owns one phase

/herdr-control · proposed rename

The plan-level TUI—the one you talk to

This is the proposed clearer internal name for today's /herdr-run. It validates the frozen plan and route, starts one fresh phase leader at a time, waits on typed phase events, applies phase-level replay/backtracking, handles human decisions, and writes the terminal run authority. It does not implement stages itself.

/herdr-phase · existing internal role

A fresh leader for exactly one phase

It translates one phase into Stage 1 implementation, Stage 2 independent audit, deterministic seam checks, merge, and cleanup orders through the UpAgent Recruiter. It owns stage retries and phase-result.json, then exits. A replay gets a new leader and fresh context.

Selected primary

GPT-5.5 · high, preferably fast mode

Use high for ordinary Stage 1 work. The plan is specific enough that xhigh on every phase is mostly extra latency and second-guessing. If fast mode spends credits faster but lowers wall-clock time, that is a sensible trade when unused credit—not scarcity—is the constraint.

Use xhigh only for the ownership/reconciliation or candidate-custody phase, or after one failed implementation pass. Keep the scope leash even at high.
Independent per-phase audit

Claude Sonnet high; Opus on the riskiest phase

Because GPT writes the code, the adversary must come from Claude—not Sol. Sonnet high should audit ordinary phases quickly. Use Opus high for the phase that changes destructive ownership/cleanup rules and for any disagreement Sonnet cannot resolve.

GPT-5.6 Sol is not the adversary when GPT-5.5 is the implementer; it is too close to the same model/provider family for the independence we want.

Fresh Claude Opus high, authoring disabled

After all phases merge and tests are green, use one fresh Opus reviewer that authored none of the changes. It reviews the whole diff, migration compatibility, and public-repository proprietary-content risk. That preserves model-family independence and can satisfy the mandatory independent review only if it explicitly returns a pass.

Custody contract

During phase work

Herdr owns the candidate branch

Phase leaders and stage workers may change it only through route-approved work. Temporary worktrees never own the shared infrastructure lane.

Candidate ready

Herdr pauses and yields custody

Record branch, exact head SHA, intent, phase evidence, dirty-state proof, gate attempt number, and the next owner. This is a checkpoint, not the terminal marker.

Gate outcome

Success ends; failure returns custody

no-mistakes exclusively owns rebase, fixes, PR, and CI. Checks passed allows Herdr terminal success. A failed shared test emits evidence and returns custody for a targeted Herdr repair pass.

no-mistakes + shared AWS reality

It fits only if CI/CD can validate an exact non-main SHA

no-mistakes is not another Herdr phase. It owns a candidate gate attempt after all planned phase work is merged but before Herdr declares terminal success. That only works if the shared environment can deploy the exact candidate or PR SHA under a remote, single-writer lease visible to every CI worker and concurrent run.

Current main-only deployment

Poor fit for an end-of-plan gate

phase worktree
└── audit
    └── merge / push main
        └── main deploys to the one AWS environment
            └── integration test
                └── next phase

If main must receive every phase before AWS can be tested, the work is already published before no-mistakes sees it. Running the gate at the very end is then post-facto review, not a gate.

Recommendation: do not add no-mistakes to this mode. Keep Herdr's current phase checks and mandatory independent review.
Target branch-SHA deployment

Good fit at the candidate-ready checkpoint 

Herdr candidate branch
└── candidate-ready receipt; Herdr pauses edits
    └── no-mistakes attempt N
        ├── rebase → review → test → docs → lint
        ├── push / update one candidate PR
        └── PR CI acquires the shared AWS lease
            ├── reconcile the one test user / baseline
            ├── deploy exact PR SHA
            ├── run global integration + acceptance
            ├── finally: cleanup + release lease
            ├── PASS → checks-passed → Herdr terminal success
            └── FAIL → evidence receipt → custody back to Herdr

All temporary phase worktrees merge into one candidate branch and one PR. The worktrees may build independently; only the branch SHA holding the central lease may touch the shared test user and AWS environment.

SHA rule: a no-mistakes rebase or fix creates a new candidate. Only the exact SHA deployed and tested under the lease may receive checks-passed.

When the one big integration loop fails 

shared acceptance FAILS on exact SHA
├── freeze integration-failure.json
│   ├── SHA + gate attempt + lease owner
│   ├── failed check / resource / test user
│   ├── commands + logs + cleanup state
│   └── changed components since last passing baseline
├── disable broad CI auto-fix for this failure class
├── no-mistakes returns branch custody
└── fresh independent triage worker
    ├── reads phase manifests, commits, handoffs, and failure evidence
    ├── phase-owned failure → revisit earliest responsible phase
    ├── cross-cutting failure → create / replay integration-repair phase
    └── ambiguous ownership → stop for human, never guess
        └── Herdr replays forward → candidate attempt N+1

This is a larger loop, but it is not “redo the whole plan.” It reuses Herdr's existing forward-only revisit mechanism. The hard new requirement is trustworthy failure-to-phase attribution backed by manifests and evidence. The language model recommends the revisit; typed files and an independent audit make that recommendation reviewable.

Practical conclusion: first prove exact-SHA branch deployment, a remote environment lease with heartbeat/TTL/final cleanup, and failure-to-phase receipts. Then pilot no-mistakes as the candidate gate loop. While deployment is main-only, skip this integration.

Guardrails

What must not happen

Do not replace typed files with terminal prose

Herdr's strongest property is reconstructable truth. Pane state, scrollback, and status prose remain observations, not completion authority.

Do not let Herdr and no-mistakes edit at the same time

At candidate-ready, Herdr must yield branch custody while the gate rebases, fixes, pushes, and runs CI. A failed gate must explicitly return custody before Herdr starts a repair pass.

Do not copy Firstmate's hooks without its predicate

The hooks depend on home identity, lock, beacon, task metadata, and watcher state. Port the invariant as a Herdr-native mechanism.

Do not call a named local remote “mandatory”

A user can still push directly to origin. Protected branches and required remote checks remain the enforcement boundary.

Do not weaken independent audit

Stage 2 must independently inspect the branch and evidence before advancing. A later global integration failure does not erase that evidence; it adds a new failure to triage and backtrack.

Decision options

Three paths

A · Minimal

Keep Herdr unchanged

Lowest change risk, but leaves delivery outside the run and misses mature lifecycle lessons from Firstmate.

Safe, limited gain
B · Recommended

Layer by role, not by force

Herdr controls phases and repair passes. Firstmate patterns harden ownership and recovery. no-mistakes owns the final candidate gate and shared-environment CI attempt.

Best capability / risk balance
C · Rewrite

Replace Herdr with Firstmate

Imports a large shell-heavy distro and still needs a runtime backend. Loses the canonical phase/stage route, typed stage gates, and phase backtracking unless rebuilt.

Not recommended
