Architecture comparison · 21 July 2026

Firstmate is the better exploration task desk.
Your TUI is the stronger context-bearing front door.

Firstmate preserves a scout’s findings through reports, status, decisions, and backlog records—not by sharing the worker’s full conversational context. That is a good fleet design, but it is only a partial match when the front TUI itself must understand the codebase and carry the onboarding journey forward. For your exact requirement, keep exploration in the current TUI with its native subagents. Reserve UpAgent for bounded ad-hoc jobs where choosing a different provider or model is the main benefit.

Unknown path

Explore with Firstmate

Chat intake becomes a bounded scout brief, an isolated worker, supervised execution, a self-contained report, and durable unresolved decisions.

Known path

Build with Herdr

A checked plan and route become phases, independent audit, seam checks, deterministic finalization, receipts, retries, and an authoritative run result.

Repeatable path

Run without either

The finished smoke test should be a deterministic Taskfile/CI command with structured pass/fail evidence. Agents diagnose or evolve it; they should not be its truth source.

The important correction

“No plan” in Firstmate does not mean “no scope.” Firstmate still writes a task-specific brief and classifies the work as a scout or ship task. What it removes is the requirement for a pre-approved, phase-decomposed plan.md + route.yaml before learning can begin.

The name collision is real

There are currently two different meanings of “Herdr”: the upstream terminal/runtime product, and your plan/phase orchestration layer built on top of it. Firstmate’s “Herdr backend” means only the upstream pane transport. Renaming your orchestration layer—or consistently calling it the plan runner until you choose a name—would make the boundary easier to explain and reduce trademark ambiguity.

Side by side

Same human experience at the top; different contract underneath

Both give you one conversational pane. Firstmate translates conversation into fleet tasks. Herdr translates an approved execution artifact into governed phases and stages.

Can Firstmate run the phases?

Technically possible; strategically weaker than keeping your plan runner

Firstmate can supervise a sequence of project tasks, but its current unit is a ship/scout task—not a parsed phase with required implementation, independent review, seam validation, and finalization stages.

What works today

Target-repository context is preserved

You operate Firstmate from its own home, but each ship or scout launches inside an isolated worktree of the selected target project. The harness therefore starts with that target repository as its working directory.

  • The target project is registered or cloned beneath Firstmate’s projects/ area.
  • Treehouse or Orca creates a disposable worktree from that project.
  • The worker sees the target project’s committed AGENTS.md/CLAUDE.md.
  • Harness-native global and target-project skills remain available according to that harness’s normal discovery rules.
So no: workers do not execute “inside the Firstmate repository” when changing another project.
What does not work today

UpAgent personas are not Firstmate dispatch profiles

Firstmate’s dispatch profile selects only a harness, model, and effort. It has no current field for an UpAgent offering/persona, no request submission to your one Hub, and no receipt translation.

  • A project-local specialist skill may load normally.
  • A Hub-selected specialist persona is a different mechanism and is not automatically selected.
  • Using a raw launch command is an escape hatch, not a designed UpAgent integration.
  • Letting both Firstmate and UpAgent own the same worktree, worker, retries, or teardown would violate the one-owner rule.
Your existing decision still stands: one UpAgent Hub only, with specialists as ordinary persona-selected orders.
Recommendation

Keep phase authority in the plan runner

Replacing each plan phase with Firstmate tasks would duplicate supervision and no-mistakes delivery while losing your strongest assets: typed stage gates, specialist Hub personas, independent audit, deterministic receipts, and phase-level replay.

Better direction: borrow Firstmate’s captain-facing experience—durable status, decision holds, restart recovery, concise reports, and optional AFK supervision—without replacing the plan runner’s execution engine.

Ad-hoc provider offload

This is the strongest reason to add a small UpAgent command surface

The target repository already imports the shared UpAgent and plan-runner justfiles. The missing piece is ergonomic delegation: send one bounded task to Codex, Claude, or a Pi offering, wait without burning the front TUI’s tokens, then bring the typed result back into the current conversation.

Already available

The Hub already has the machine primitives

No request JSON is required: the public facade accepts named flags and the target justfile exposes them now. 

just upagent lists --type offerings
just upagent request --type worker \
  --offering <id> --effort <level> \
  --agent <persona> --prompt-file <absolute.md> \
  --cwd <target-repo> --wait --json
  • status --request retrieves typed request state.
  • lists --type workers lists active or terminal workers.
  • await blocks in Python rather than spending LLM turns.
  • reconcile repairs expired or orphaned owned runtime state.
Important lifecycle distinction

Get, cancel, and cleanup are three different operations

  • Get is read-only: request state, verdict, summary, handoff, receipt, and log pointer.
  • Cancel stops a live owned request. Today, public cancel exists only as a fenced response when the Hub reaches a requester decision point—not as an arbitrary anytime command.
  • Cleanup must mean pruning terminal history/artifacts. Worker and manager panes are already identity-checked and closed automatically before a terminal receipt.
  • Reconcile is the existing runtime repair command; it is not history deletion.
Do not call one ambiguous command delete or destroy. It would be unclear whether it kills a live worker, removes evidence, or both.

Is Firstmate “AFK a lot”?

It is asynchronous by default, but AFK mode is optional

Normal Firstmate supervision stays live while work is under way and wakes on actionable events. The explicit /afk mode is a separate, presence-gated sub-supervisor for when you actually leave.

  • Workers are autonomous and are told not to wait for a human.
  • The normal rhythm is checkpoint-based: brief, work, decision, outcome.
  • Firstmate does not continuously pair-drive the worker or read its chat.
  • You may type directly into a worker pane; Firstmate treats that as authoritative and reconciles it later.
Experience tradeoff

For continuous pair-driving, a direct TUI can still be better

If you expect to comment on every screen and choose every next action in real time, Firstmate’s liaison layer can feel indirect. Use one direct interactive QA agent with the same ledger template, or explicitly brief a Firstmate scout to pause at named checkpoints.

Firstmate wins when the walkthrough lasts hours, survives interruptions, branches into investigations, or must leave a durable report and decision inventory. Direct TUI wins for a short, tightly coupled pair session.
Does the crewmate’s context disappear?

The evidence persists; the shared working mind does not

What the Firstmate liaison keeps
  • The original brief and task metadata
  • Status and decision-hold records
  • A required self-contained scout report
  • The journey ledger if the brief requires it
  • Backlog pointers and durable project knowledge
What it deliberately does not keep
  • The worker’s whole chat or implicit reasoning
  • Every screen-level observation unless recorded
  • Scratch edits after scout teardown
  • A continuously shared code-reading context window
What the liaison can still do
  • Read the target project clone and README/code when routing
  • Read and relay the completed scout report
  • Reference that report in the next task brief
  • Promote stable knowledge into the project’s AGENTS.md
A persistent secondmate can retain a domain home and supervise later crews, but it still communicates upward through status/documents rather than shared chat. It reduces restart loss; it does not turn the fleet into one continuous context window.
Closer match for your requirement

Separate interactive exploration from provider offload

flowchart LR U["You + context-bearing TUI\nreads target repo"] --> S["Native harness subagents\ninteractive exploration support"] S --> L["Journey ledger\nissues + evidence + decisions"] L --> U U --> A["/upagent-run\nbounded alternate-provider job"] A --> U U --> P["Normal research / planning"] P --> R["Plan runner implements phases\nthrough the same one Hub"]
  • Front TUI owns onboarding continuity: it talks with you, drives the UI, reads code, and maintains the journey ledger.
  • Native subagents support exploration: use the current harness’s interactive delegation when shared conversational context matters.
  • UpAgent spreads provider usage: send bounded commands, tests, audits, or investigations to a chosen Codex, Claude, or Pi offering.
  • Planning remains separate: empirical findings become research input; fixes begin only after the normal plan is approved.
Revised practical answer: keep onboarding in the context-bearing TUI and its native subagents. Use Firstmate only for asynchronous fleet work, and use the new thin UpAgent commands for bounded alternate-provider offload. These are three different jobs; forcing one tool to own all three would make each experience worse.

Clean complement

  1. Firstmate scout discovers and records the behavior.
  2. Human resolves product/test decisions.
  3. Planning converts the stable report into an approved plan.
  4. Herdr implements the plan and publishes terminal evidence.
  5. no-mistakes takes exclusive delivery custody.
  6. The resulting deterministic smoke command runs routinely.

Bad nesting

  • Firstmate spawns a worker that starts a Herdr run and both watchers supervise it.
  • A Herdr stage worker starts Firstmate or delegates further work.
  • Firstmate’s no-mistakes mode starts before Herdr finalization releases branch custody.
  • Both systems believe they may close the same pane or remove the same work area.
  • A routine smoke test passes because an agent “interpreted” a failed assertion.
Herdr naming hazard: Firstmate can use Herdr as an experimental terminal/session backend. That is only pane transport. It is not your Herdr plan controller. For a pilot, use Firstmate’s reference tmux backend so the operational boundary is obvious; add the Herdr backend later only if its native pane state is worth the extra ambiguity.
Recommended operating policy

A small set of rules keeps the systems coherent

Rule 1

Discover before planning when needed

Use a Firstmate scout only when the behavior, failure, or test boundary is genuinely unknown.

Rule 2

Plan before changing

A scout report is evidence. Code changes still require explicit implementation authorization and, for meaningful work, the normal plan path.

Rule 3

One orchestrator at a time

Never let Firstmate and Herdr co-own workers, work areas, branches, decisions, or cleanup.

Rule 4

Automate agents out of the happy path

When a user story stabilizes, convert it to a command. Keep agents for diagnosis, adaptation, and planned repair.

Pilot recommendation

Prototype the context-bearing exploration loop before adopting Firstmate

  1. 1. Keep the interactive TUI rooted in the actual target repository so it can read code and talk with you directly.
  2. 2. Create one run directory with a compact current summary, journey ledger, issue inventory, decisions, and evidence.
  3. 3. Dispatch one ordinary UpAgent scout order with the best specialist persona and explicit target working directory.
  4. 4. Require the scout to update the ledger/report; then have the TUI read it before the next conversation or order.
  5. 5. Once findings stabilize, hand the artifact to the normal research/planning front door—do not fix opportunistically.
  6. 6. Use the plan runner and the same one Hub for approved phases; keep no-mistakes downstream for delivery.
