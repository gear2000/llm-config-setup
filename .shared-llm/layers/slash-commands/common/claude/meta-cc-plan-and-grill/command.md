# /meta-cc-plan-and-grill

Convenience wrapper concept for preparing a Meta-CC run. It keeps planning and meta execution separate.

## Invocation

```text
/meta-cc-plan-and-grill <normal cc-plan-and-grill arguments> --route <route.yaml>
```

`--route <route.yaml>` is the output path for the route profile generated by this command — the second file (alongside `plan.md`) required for a runnable Meta-CC input. It does not need to exist yet; this command writes it.

## Behavior

1. Run the normal `/cc-plan-and-grill` front-door planning flow. Do not redefine or fork its planning semantics.
2. Run `/meta-plan-convert` on the approved plan when it is not already in canonical shape.
3. Produce the required two-file runnable input shape, writing the route profile to the path given by `--route`:
   - `plan.md` — one `# Plan:`, one `Goal:`, ordered `## Phase <N> — <title>`, required `Done:`, optional `Ideal:`, no routing;
   - `route.yaml` (the `--route` path) — `llm_profiles`, worktree branch template, finalization checks, per-phase `merge_back_at`, and every phase lead/stage with `llm_profile` and `agent`.
4. During the grill, ask the user for each phase whether it should merge back at Stage 3, Stage 4, or Stage 5. Do not leave runtime leads to decide merge timing.
5. Run `/meta-plan-check <plan.md> <route.yaml>` (the file written to `--route`) and report whether it is runnable.
6. If routing, merge timing, worktree, or finalization checks are incomplete, leave `route.todo.yaml` / TODO fields at the `--route` path and ask the user to complete them before execution.
7. Tell the user to launch `/meta-cc --plan <plan.md> --route <route.yaml> --output-dir <dir>` only after the check passes.

## Hard rules

- This is a wrapper around planning plus meta-plan normalization, not a new planning system.
- `cc-*` commands remain front-door workflow commands and are not rebranded as meta runners.
- Do not run implementation from this command.
