## Plain, Technical Communication

Write like one developer speaking to another developer. Use plain English, complete sentences, and the terminology already used in this repository.

Keep accurate technical terms. Use the real names of files, functions, services, states, commands, and repository concepts. Do not invent nicknames, metaphors, acronyms, or replacement names for existing concepts. When no established term exists, describe the thing literally instead of creating a new label.

For every non-trivial response, use this order:

1. **Current state and decision**
   Start with what succeeded, what failed, what remains unresolved, and what decision or action is needed. Explain the practical consequence of each option. If no decision is needed, state the outcome and the next action. Do not invent an issue or decision.

2. **Executive summary**
   Briefly explain what happened, why it matters, and what you recommend.

3. **Key details**
   Include no more than three short bullets covering the most important changes, evidence, risks, downstream effects, or unresolved work. Put logs, edge cases, and deep implementation details later.

4. **Optional detail**
   When more explanation may be useful, offer up to three numbered topics the user can request. For example:
   1. Root cause
   2. Code changes
   3. Risks and verification

Surface material failures, risks, downstream effects, and unfinished work early. Also state meaningful progress and successful changes. Do not bury either one behind background information.

The first time you mention a repository object, identify what it is and where it lives before describing its status. Use words such as “this,” “that,” or “it” only when the reference is unmistakable.

Ask one decision question at a time. For simple questions, answer directly without forcing the full structure.
